# Conservative stack-slot planning, revision 1

Implemented as an opt-in backend optimization. Consume verified
IR and semantic liveness without removing instructions or changing SSA IDs.
The planner is separate from machine-code emission and precise GC root maps.

`ir::storage::planSlots(program)` returns `Result<ProgramSlots, string>`:

```text
ValueSlot { valueId: int, index: int }
FunctionSlots { functionId: int, values: Vec<ValueSlot>, slotCount: int }
ProgramSlots { functions: Vec<FunctionSlots> }
```

Every formal parameter, block parameter and instruction result with a
nonnegative ID receives exactly one eight-byte slot. Use original definition
order: formal parameters, then each block's parameters and instruction results.
Function output order follows the program. IDs can be sparse; storage must not
scale with maximum ID. Input IR is immutable and output vectors independent.

Build interference from these conservative rules:

- All values simultaneously live in each block/instruction/terminator snapshot
  conflict pairwise. Include liveIn, liveOut, liveAtTerminator, liveBefore and
  liveAfter, preserving conservative cross-edge conflicts.
- Every instruction definition conflicts with all different values live after
  it, even when the definition's result is dead. Emission still stores it.
- All formal parameters conflict pairwise, including dead ones. The prologue
  stores every parameter.
- All parameters of each block conflict pairwise, including dead ones. Each
  block parameter also conflicts with every different value live at that
  block's entry. Edge emission writes every target parameter, so a dead one
  must not overwrite a live dominating value.

The backend loads operands before storing an instruction result, and copies
every edge argument through a separate scratch area before writing any target
slot. Dying operands may therefore share the result slot. Scratch bytes are
not colored or included in slotCount. Code generation must size its frame from
slotCount, never from the number of mapping entries.

Greedy coloring in definition order chooses the lowest available nonnegative
index. Slots must be contiguous from zero to slotCount minus one, with zero
for a function having no definitions. Deterministic output is required; optimal
coloring is not. Reject invalid IR and propagate liveness errors. A separate
deterministic work budget bounds interference/coloring work after verification
and liveness; exhaustion returns an error, never a partial or unsafe layout.
The verifier and liveness have their own costs and limits.

Fixtures must include sparse IDs, straight-line reuse, unused results writing
across live values, dead formal/block parameters, live non-parameter values
across edges, parallel swaps, loops, calls/recursion, raw addresses, void-only
functions, repeatability, malformed IR and input/output mutation independence.
Check every reported conflict has different slots using an independent test
oracle. Plan existence and a smaller frame are not runtime speed measurements.
Backend opt-in wiring and actual differential execution are a separate gate.

The coordinator integrated `emitArm64WithReuse(program, os)` and
`emitProgramWithReuse(program, "linux-x64")`; default emitter APIs retain their
original behavior. The experimental native driver uses `--reuse-slots`, which
may combine with `--fold-constants` and `--std-root`. It is off by default.
Plan errors propagate without an unsafe partial layout. Runtime fixture
harnesses may accept the same trailing flag for separate default/reuse gates.

The planner uses sparse-ID maps and deduplicated adjacency lists rather than
repeated global pair scans. Its one-million-unit work budget is unchanged.
The source integration gate passes 396 checks in reuse/folded-reuse modes:
`build/v04/opt-integration/storage-reuse-2/result.json`. Direct-IR execution
passes 69 checks across 34 images in both modes:
`build/v04/native-storage/parent-2/result.json`. The chain fixture maps 41
definitions to two slots; decoding the emitted ARM64 prologue confirms its
frame changes from 336 to 16 bytes. This is a frame-size observation, not a
runtime speed measurement. Linux x64 execution is emulated; native x64
hardware remains unverified.
