# Rey v0.4 design

Status: proposal, 2026-10-17. Not a change to `SPEC.md`. Nothing here is implemented in the compiler or the runtime.

This is the native-runtime and language-surface plan for the version after v0.3. It is based on the v0.3 value model and on benchmarks run on this machine. Estimates are marked as estimates. Numbers without that label come from the runs listed in section 11.

Decision rule used throughout: prefer the option that is faster, smaller to implement, smaller to use, easier to work with, and more memory efficient. Where those conflict, the text says which one won and why.

## 1. Decisions

1. **Memory.** The native runtime gets a non-moving **mark-region collector**. Object allocation is a thread-local bump pointer into 64 KB blocks divided into 128 B lines. There is no evacuation. Reference counting is not the primary mechanism. Regions are not the primary mechanism. The Rust oracle keeps `Rc<RefCell<_>>` and is not rewritten.
2. **Cycles.** They stay legal. The collector reclaims them. The language does not grow weak references, and it does not forbid a struct from pointing at itself.
3. **Buffers.** Vec and HashMap storage stays uniquely owned by its header and is allocated with system `malloc` / `realloc` / `free`. It is not bump-allocated, and it is not allocated with raw `mmap`.
4. **Threads.** Two constructs: `parallel for` over an integer `range`, and `spawn` / `Task<T>.join()` for values that are copied (`int`, `float`, `bool`, `char`, `string`, and tuples / enums / `Option` / `Result` made only of those). No channels, no shared mutable aggregates, no task I/O, no global `var` access. A fixed work-stealing pool is created once at startup.
5. **Bits.** `int` gets `~ & | ^ << >> >>>`, checked shift counts, and `popcount` / `clz` / `ctz`. No `u8` / `u16` / `u32` / `u64` / `i32`, and no second byte-buffer type. Unsigned order is four methods on `int`.
6. **SIMD.** No vector types. User programs are compiled at `-O2` with floating-point contraction off, and loops are emitted so LLVM can vectorize them.

## 2. What v0.3 actually is

Relevant semantics, all already decided:

- `int` is signed 64-bit. Overflow, divide by zero, and `INT64_MIN / -1` are runtime errors (`SPEC.md` §6.3).
- Structs, Vecs, and HashMaps are shared mutable references. Assignment copies the reference. Equality is identity. `const` does not freeze the object (`SPEC.md` §11).
- Strings, scalars, tuples, enums, `Option`, and `Result` are copied by value. A reference stored inside a tuple is still shared (`SPEC.md` §4.3).
- A lambda snapshots scalars and strings and shares aggregates. It cannot reassign a capture.
- Those rules allow cycles. A struct field can hold another struct, a Vec can hold a struct that holds that Vec, and a closure can be stored in a struct it captures. Nothing in the spec forbids it.
- Bitwise operators, `uint`, `byte`, and `double` are out of v0.3 (`SPEC.md` §12, charter decision 12).

Relevant implementation facts:

- `rey_alloc` is `malloc` plus `memset`, and nothing frees ordinary objects (`rey-compiler/runtime/mem.c`). Sanitizer leak detection was intentionally disabled for this. That is process-lifetime allocation, not a memory manager (`docs/HANDOFF-2026-10-17.md`).
- Vec growth does `free` the old element buffers (`rey-compiler/runtime/vec.c`). Those pointers come from `rey_alloc`. Any future split between a garbage-collected heap and a buffer heap has to keep that `free` on the buffer heap.
- Strings are interned in a process-lifetime pointer table (`rey-compiler/runtime/string.c`, `registerStringPointer`). That table only grows. A collector must not treat it as a root set, or no string will ever die.
- The Rust oracle already stores aggregates in `Rc<RefCell<_>>` (`compiler/v1/src/interpreter/executor.rs`). Rust's `Rc` is not atomic and does not collect cycles. The oracle is single-threaded.
- Regions and promotion were left as future work by the v0.3 handoff. They are not a committed design.
- Codegen is about 5,800 lines of Rey, the checker about 4,100, the C runtime about 2,900, the Rust interpreter about 8,500. The native compiler is not self-hosting. A memory plan that needs a new middle end in the Rey compiler is more expensive than the same feature written once in C.

## 3. Measurements

Machine: Apple M1, 8 logical cores (4 performance + 4 efficiency), 8 GB RAM, 16 KB pages, `hw.optional.arm.FEAT_LSE = 1`, Apple clang 21.0.0, `-O2` unless noted. The machine was shared. Medians of several trials are reported; the reproduce script is section 11. These are microbenchmarks, not Rey programs.

### 3.1 Small allocation

Single thread, warm steady state, one byte written per object so the allocation is not deleted. `malloc_free` is the alloc/free pair. `bump_warm` is allocation only, into memory that was already faulted; it does not free.

| Operation | 32 B, ns/op |
|---|---:|
| `malloc` + `free` | 48.2 |
| `malloc` + `memset` + `free` | 51.0 |
| thread-local freelist + `free` | 10.9 |
| freelist + zero + `free` | 22.1 |
| bump, already faulted | 2.65 |
| bump + `memset` | 10.4 |
| `malloc` of a fresh object, freed after the timer | 32.0 |

The same shape holds from 16 B through 4096 B: the freelist pair is roughly 4–8× the `malloc` pair (16 B: 6.1 ns vs 47.7 ns; 4096 B: 15.3 ns vs 61.5 ns). Full table: `results/alloc.txt`.

Zeroing a 32 B bump allocation costs more than the bump itself (10.4 vs 2.65). `rey_alloc` currently zeros every object.

Throughput of a 32 B `malloc`/`free` pair, wall time of the slowest thread, total ops across threads:

| Threads | malloc, million pairs/s | freelist, million pairs/s | bump alloc, million/s |
|---:|---:|---:|---:|
| 1 | 18.0 | 79.9 | 412 |
| 2 | 29.8 | 180 | 655 |
| 4 | 46.5 | 286 | 688 |
| 8 | 42.9 | 633 | 2900 |

`malloc` is slower at 8 threads than at 4. The freelist keeps scaling. The 8-thread bump figure is not consistent with the 2→4 step (4 threads were already down to 688 million/s), so 2.4–2.7 ns/op single-thread is the number to plan with, not the 8-thread burst. Each bump "allocation" writes one byte; it is a pointer-bump benchmark, not a full-object initialize.

### 3.2 Large objects and Vec growth

| Operation | ns/op |
|---|---:|
| `malloc`/`free` of 64 KB | 320 |
| `mmap`/`munmap` of 64 KB | 7072 |

Raw `mmap` is 22× slower than `malloc` at 64 KB. macOS has no `mremap`.

Growing an `int64` buffer from 0 to 1,000,000 elements by doubling, median of 7 runs, nanoseconds per pushed element:

| Strategy | ns/element |
|---|---:|
| `malloc` + copy + `free`, which is what `vec.c` does | 4.38 |
| `realloc` | 3.66 |
| freelist up to 4096 B, then `malloc` | 5.35 |

The copy dominates. A custom freelist does not help this workload. `realloc` is the best of the three.

### 3.3 Reference counting

All single-thread numbers are hot in L1. They are not a cache-miss estimate.

| Operation | ns/op |
|---|---:|
| volatile increment of one `uint64` | 0.34 |
| volatile inc+dec pair (non-atomic RC) | 2.56 |
| `memory_order_relaxed` atomic inc+dec pair | 3.86 |
| `memory_order_acq_rel` atomic inc+dec pair | 14.2 |
| plain pointer store into a 4096-slot table | 0.32 |
| that store plus a non-atomic retain/release | 2.12 |
| load of a gc flag that is never set | 0.32 |

Uncontended relaxed atomics are close to a volatile inc/dec (3.86 vs 2.56). Acquire/release is the expensive uncontended policy, not the atomic RMW by itself. A non-atomic retain/release makes a hot pointer store about 6.6× more expensive (2.12 vs 0.32), which is real but small next to a cache miss.

Four threads doing `memory_order_acq_rel` increments of **one** counter: 88.4 ns per increment on each thread (2,000,000 increments each, slowest thread 177 ms). Contended reference counts are a different regime from thread-local ones.

A 200,000-node acyclic list, each node `rc == 1`, frees in 8.0 ns/node including `free`.

A ring of 100,000 nodes, each `rc` held by the next node, plus an external root that is then dropped: **100,000 nodes stay at `rc > 0`**. Naive reference counting leaks the cycle. That is the whole result of `CHECK rc_ring`.

### 3.4 Mark-region collector

Prototype: 64 KB blocks, 128 B lines, no copying, precise roots passed in an array. Header in the bench is 16 B; that header is a bench device, not a proposed ABI change (section 4).

| Check | Result |
|---|---|
| Two objects pointing at each other, root dropped | 2 live → 0 live |
| Ring of 50,000 objects, root dropped | 50,000 live → 0 live, next allocation succeeds |
| Word buffer holding the object's address | 1 object marked |
| Word buffer holding `address+1`, `address+8`, and `42` | 0 objects marked |
| Volatile stack slot holding the only pointer | object survives, magic byte intact |

Nursery workload: 2,000,000 allocations of 32 B, 8,192 roots, collection every 250,000 allocations. `malloc` frees the overwritten slot immediately. The collector does not.

| Collector | ns/op | max pause | resident during the run | bytes reachable | bytes kept by line marks |
|---|---:|---:|---:|---:|---:|
| `malloc` / `free` sliding window | 17.5 | none | not sampled mid-run; 3.0 MB after teardown | 256 KB live by construction | — |
| mark-region, roots are the last 8192 objects | 4.58 | 81–85 µs | 11.1 MB | 262,144 | 262,144 |
| mark-region, roots scattered | 7.95 | 0.46–0.50 ms | 12.0 MB | 262,144 | 995,712 |

127 blocks × 64 KB = 8.1 MB of heap for 256 KB of reachable objects. The extra resident memory is retained empty blocks, not line fragmentation: in the sliding-window run, pinned bytes equal reachable bytes. In the scattered run, 128 B lines retain 3.8× the reachable bytes (995,712 / 262,144). Nine collections, pauses summed to 0.72 ms (packed) and 4.1 ms (scattered).

The throughput win over `malloc`/`free` is measured. The resident-memory comparison against a freeing allocator is not a win for this prototype: it kept the whole 8 MB wave. Section 4 says surplus empty blocks go back to the OS. That return path was **not** in the timed prototype.

### 3.5 Work stealing

Chase-Lev deque with the PPoPP 2013 memory orders. Every parallel run below was checked against the serial result. The pool is created inside the timed region, so short runs include `pthread_create`. Default thread QoS: the OS may put workers on efficiency cores. One thread of pool overhead is visible: serial mix of 10^7 elements is 8.35 ms, the same work through one worker is 14.0 ms.

Uniform mix over 10^7 `uint64`s (one `mix64` per element):

| Run | Time | vs serial |
|---|---:|---:|
| serial | 8.35 ms | 1× |
| static split, 4 threads | 3.07 ms | 2.72× |
| steal, chunk 8192, 4 threads | 3.11 ms | 2.69× |
| steal, chunk 256, 4 threads | 4.13 ms | 2.02× |
| steal, chunk 65536, 4 threads | 3.10 ms | 2.69× |

On uniform work, stealing matches a static split once the chunk is a few thousand elements. A 256-element chunk is 33% slower than 65536.

Front-loaded work: 4×10^6 elements, the first eighth does 12 mixes and the rest do one.

| Run | Time | vs its serial (12.25 ms) |
|---|---:|---:|
| static, 4 threads | 9.08 ms | 1.35× |
| steal, chunk 8192, 4 threads | 3.31 ms | 3.70× |
| static, 8 threads | 8.47 ms | 1.45× |
| steal, 8 threads | 2.57 ms | 4.77× |

Static split gives the heavy prefix to thread 0. Stealing is 2.7× faster than static at 4 threads on this input (9.08 / 3.31).

Same uniform mix over 10^8 elements, one run, input RSS 801 MB:

| Run | Time | vs serial |
|---|---:|---:|
| serial | 89.0 ms | 1× |
| static, 4 threads | 41.2 ms | 2.16× |
| steal, chunk 65536, 4 threads | 37.6 ms | 2.36× |

Four threads give about 2.2–2.7× on uniform data, not 4×. That is the measurement on this shared M1. It is not a basis for promising linear speedup.

### 3.6 Vectorization and floating point

Sum of 10^7 `int64`s. Clang remarks are in `results/vecpass.txt`. The vectorized loop is width 2, interleaved 4, which on this target is NEON.

| Loop | Opt | ns/element |
|---|---|---:|
| plain sum | `-O2` | 0.140 |
| plain sum | `-O2 -fno-vectorize` | 0.366 |
| plain sum | `-O0` | 0.961 |
| bounds check written inside the loop | `-O2` | 0.136 |
| bounds check in a `noinline` function | `-O2` | 0.990 |
| per-element indirect call | `-O2` | 0.960 |
| `__builtin_popcountll` | `-O2` | 0.142 |
| `__builtin_popcountll` | `-O2 -fno-vectorize` | 0.412 |
| 64-step software popcount | `-O2`, 2×10^5 elements | 7.87 |

The inlined check vectorizes and matches the plain sum. A call per element does not vectorize and is about 7× slower. `otool` shows `cnt.16b` in the vectorized popcount. The software loop is 55× slower per element than that builtin.

`return a * b + c` with `a = b = 0.1` and `c = -0.01`:

| Flags | Instruction | Bits | Value |
|---|---|---|---|
| `-O0` and `-O2`, default contraction | `fmadd` | `0x3c30a3d70a3d70a4` | 9.0205620750793972e-19 |
| `-O2 -ffp-contract=off` | `fmul` then `fadd` | `0x3c40000000000000` | 1.7347234759768071e-18 |

Default clang fuses that expression even at `-O0`. SPEC §6.3 says float arithmetic follows IEEE-754. A fused multiply-add is a different operation from a multiply followed by an add. The two results differ at this input.

## 4. Memory management

### 4.1 Why mark-region, not reference counting

Perceus (Reinking, Xie, de Moura, ICFP 2021) inserts `dup` and `drop` in the compiler, borrows non-escaping uses, and reuses a unique dead object for the next allocation of the same shape. Lean does the same class of thing (Ullrich and de Moura, "Counting Immutable Beans"). The reuse result is what makes reference counting competitive with a tracing collector **for immutable functional updates**.

Rey does not need that reuse result. A struct field write and a `Vec.push` already mutate the existing object. The expensive thing Perceus recovers is the language's ordinary case.

What reference counting would still be for is reclamation. Three measured and structural problems keep it from being the primary plan:

1. **Cycles leak.** Section 3.3 retained every node of a 100,000-node ring. Section 3.4 reclaimed a 2-cycle and a 50,000-node ring. A backup cycle collector (Bacon and Rajan, ECOOP 2001) is a second collector. CPython is the existence proof that reference counting plus a cycle collector works, and also that it is not a small runtime. Shipping both fails "smaller."
2. **The compiler change is the wrong shape for this codebase.** Precise `dup`/`drop` has to be inserted by the Rey codegen, which is not self-hosting. A missed `dup` is a use-after-free. A missed root in a non-moving collector is also a use-after-free, but the root set is "every pointer alloca," which is a regular set. The `dup` set is "every copy." The oracle would not get Perceus either: it already clones `Rc` on value copies, which is naive reference counting, and it would keep leaking cycles.
3. **Uncontended atomics are not the reason.** Relaxed atomic pairs cost 3.86 ns against 2.56 ns for a volatile pair. Rejecting reference counting because "atomics are slow" would not match this machine. Contended counts are slow (88 ns), and the thread model in section 6 does not share mutable objects, so a thread-local count would have been viable. Cycles and compiler size are the reasons.

Failure mode we accept: the collector is non-moving, so a bad root **leaks or frees early**. Early free is prevented by over-approximating roots (section 4.3), never by under-approximating them. A moving collector would need precise stack maps and forwarding; that is more compiler than v0.4 should take on.

### 4.2 Why not regions as the primary mechanism

A region dies all at once when its scope ends. That is fast, and the bump numbers in section 3.1 are what it would feel like. It is a bad primary mechanism here for three reasons.

- Escape analysis on this language is a borrow checker. Any store into a struct, a Vec, a HashMap, a global, or a closure can make an object outlive the scope. Getting it wrong is a use-after-free, not a leak.
- The heaps that matter in a compiler — AST nodes, symbol tables, closures — are exactly the objects that escape the allocating function and that can be cyclic. They need a real heap.
- The allocation fast path regions would add is the fast path the collector already has (2.65 ns once pages are faulted). Regions only add a cheaper *free*. That is worth doing later for allocations the compiler can prove do not escape, as an optimization on top of a correct heap. It is not the thing that makes the heap correct.

The v0.3 handoff's "regions/promotion" idea is this optimization, deferred. v0.4 does not block on it.

### 4.3 Collector design

**Heap.** Blocks of 64 KB from `mmap`, which is four 16 KB pages on this machine. Each block has a side line map, one byte per 128 B line in the prototype, a bit per line in production. Objects are allocated by bumping the thread's current block. A thread that fills a block takes an empty block from a per-thread cache, then from a global cache. There is no per-object free list on this path, because objects are not freed individually. The freelist in section 3.1 is the evidence that a sharded free list beats `malloc` at alloc/free of small objects; it is not the object allocator, because the collector does not free small objects one at a time.

**Large objects.** Anything that does not fit in a half-used block and is over 8 KB is allocated with `malloc`, stored in an explicit large-object list, and freed at sweep if unmarked. The 8 KB cutoff was not tuned. The measured fact that motivates `malloc` rather than `mmap` is the 22× gap at 64 KB. Strings larger than 8 KB and any object larger than a block use this list. Their existing header layout stays.

**Existing ABI stays.** `CONTRACTS.md` layouts are not widened with a reference-count or mark word. Mark bits live in the side line map plus a side bitmap of object starts (the prototype used an in-object mark byte and a 16 B bench header; production must not). String pointers still point at the data, 16 B after the header. The tracer subtracts 16 and checks `REY_TAG_STR`. A root is the base data pointer, not a pointer into the middle of the bytes. Derived interior pointers are recomputed after a safepoint, not stored across one.

**Tracing.** One C walk understands the existing tags:

| Tag | What is traced |
|---|---|
| string | nothing inside |
| struct | pointer fields described by the type-id table codegen emits |
| enum, tuple, option, result, closure env, dynamic box | slots whose kind is a pointer kind |
| Vec, HashMap | the header, then elements whose kind is a pointer kind; the element storage itself is a buffer, not a collectable object |

`REY_SLOT_RAW` is treated as a non-pointer. Putting a heap pointer in a raw slot is a codegen bug, same as a missed root. Typed lowering already has `rey_vec_push_typed` and the kind enums in `rey_rt.h`.

**Roots.** Codegen keeps a shadow stack. Every alloca that holds a pointer (string, struct, Vec, map, closure, task, box, enum, tuple) is pushed for the whole function, and popped on exit. Pushing for the whole function, rather than for the precise live range, retains extra garbage and does not free early. That is the trade we want. Integers and floats are not pushed. A conservative scan of the Rey frame is the wrong default: section 3.4 shows that an `int` whose bits happen to be an object address would keep that object, and Rey stores pointers in `i64` registers. The C runtime does not leave Rey pointers in C locals across a collection except in explicit root arrays, which is what the bench did.

The stack-scan smoke test succeeded for a volatile C local. That shows a scan can see a spilled pointer. It does not override the integer false-positive result, so generated Rey frames use the shadow stack anyway.

**Safepoints.** A collection is requested by setting one global flag. `rey_alloc` and every runtime function that can allocate check it. Loops that call those functions safepoint inside the call. Loops that do not allocate and do not call poll **between chunks**, not per element. Section 3.6 shows a call inside a 10^7-element loop costs the vectorization (0.99 ns vs 0.14 ns). An unconditional poll is 0.32 ns, which would be several times the body of a vectorized sum if it were per element. A poll every 8,192 elements is one load per chunk and was not timed separately; the arithmetic on the 0.32 ns figure is 0.32/8192 ns/element, which is below the noise of the sum.

**Trigger and pause.** Collection runs when a thread cannot get a block without growing the heap past `max(8 MB, 2 × bytes pinned at the last collection)`. That formula is a starting heuristic, not a tuned result. The measured pauses are 85 µs for an 8 MB packed heap and 0.5 ms for the scattered one. Pause cost tracked the heap that was swept, not just the live set, because sweep walks every block. A multi-hundred-megabyte heap was not measured. Do not quote the 85 µs number for one.

**Returning memory.** After a collection, empty blocks beyond a small per-thread cache (start at 1 MB) are `munmap`ed. The prototype did not do this, and its 11 MB resident set for 256 KB live is the reason the requirement exists. Whether that cache size is right is open; the requirement is that the steady state is not "every byte ever allocated."

**Threads.** Each worker bumps into its own block, so the fast path takes no lock. A collection is stop-the-world: the requesting thread sets the flag, every thread finishes its chunk or its runtime call, then one thread marks and sweeps. Parallel marking is out of scope. v0.4.0's `parallel for` body does not allocate if it only reads and writes `int` elements, so a numeric chunk never enters the collector. The worst added latency is one chunk.

**Cycles.** No language change. No weak references. No user-written "break the cycle." A cycle the program can still reach from a root stays, which is correct. A cycle it cannot reach is reclaimed at the next collection.

**Oracle.** No collector in the Rust interpreter. `Rc` already matches observable identity, mutation, and aliasing. It leaks cycles. Collection timing is not observable: there are no finalizers, and this design does not add `liveBytes` or a finalizer. A program that retains a huge cycle can run out of memory on the oracle and not on the native runtime. That is a known engine difference, not a conformance test. Differential testing stays on stdout and exit status. A native-only soak test covers reclamation.

**What this does not claim.** It does not claim lower RSS than `malloc`/`free` for an acyclic sliding window. Section 3.4 shows the opposite for the prototype. It does claim reclamation of garbage the v0.3 native runtime keeps forever, including cycles, with an allocation fast path that measured 2.65 ns against 32 ns for a fresh `malloc`.

## 5. Allocator API

Two heaps, because the measurements say they want different policies.

```c
void* rey_gc_alloc(int64_t size, int32_t typeId);  /* bump; traced; not individually freed */
void* rey_buf_alloc(int64_t size);                 /* malloc */
void* rey_buf_realloc(void* p, int64_t oldSize, int64_t newSize);
void  rey_buf_free(void* p);
void  rey_safepoint(void);
void  rey_root_push(void* slotAddress);
void  rey_root_pop(int32_t count);
```

`rey_alloc` remains as a wrapper so existing call sites keep compiling, but Vec and HashMap buffers move to `rey_buf_*`. Object headers, small strings, enums, tuples, closures, and boxes move to `rey_gc_alloc`. `vec.c` must stop calling C `free` on a pointer that came from the collector. Today that `free` is only safe because `rey_alloc` is `malloc`.

`rey_buf_realloc` is the growth path. It won the 1,000,000-element measurement. The collector, when it sweeps a dead Vec or HashMap, calls `rey_buf_free` on the buffer. The buffer is not traced as an object; its pointer fields are traced as a side table of the header. A buffer pointer is unique: no Rey value points into it except the owning header. Codegen must not stash a raw element pointer across a safepoint without also rooting the header.

Zeroing: `rey_gc_alloc` does not `memset` the payload. The caller writes the tag, the length, and every pointer field before the next safepoint. Padding can be garbage. This is the 2.65 ns path rather than the 10.4 ns path. Pointer fields that the tracer will read are the ones that must be nil or valid.

The sharded freelist (powers of two from 16 to 4096, 64 KB pages, thread-local, no cross-thread free in the prototype) stays in the scratch tree as a measured alternative. It is not part of v0.4, because object allocation does not free individually and buffer growth was faster with `realloc`. If a later profile shows small buffer alloc/free inside the allocator dominating, that file is the starting point. Cross-thread free was not implemented and was not measured; the contended-atomic number in section 3.3 is the warning that a shared free list would need real design work (a per-page remote list, owner-only recycle, tagged pointers). Do not ship a half-built Treiber stack there.

## 6. Parallelism

### 6.1 Surface

```rey
parallel for i in range(0, xs.len()) {
    ys[i] = xs[i] * xs[i] + xs[i];
}

let left: Task<int> = spawn fib(n - 1);
let right: Task<int> = spawn fib(n - 2);
let total = left.join() + right.join();
```

`parallel` and `spawn` are keywords. `join` is a method, so it is not a keyword. `Task<T>` is a built-in applied type in the same sense as `Vec<T>`: checked, then erased to a runtime handle. No user-written generic is added.

That is the whole v0.4 concurrency surface. Channels, detached threads, mutexes, and shared mutable structs are not in it. They reintroduce races and blocking, and they are more language than this version needs for parallel compute.

### 6.2 `parallel for`

Grammar: `parallel` `for` IDENT `in` `range` `(` expression `,` expression `)` block.

Rules:

- The iterator variable is a fresh `int`. The body cannot assign it.
- The range is half-open, same as `range` in `for`.
- The body is **isolated** (section 6.4).
- The only mutation allowed is `vec[i] = ...` or `vec[i] += ...` (and the other integer compounds), where `i` is exactly that iterator variable, not `i + 1` and not another expression. The Vec's static element type is `int`, `float`, `bool`, or `char` for v0.4.0.
- The Vec that is written is not read in the body. Reads of other Vecs and of struct fields are allowed. This is stronger than "distinct indices" and it is checkable without an alias analysis.
- No nested `parallel for`, no `spawn`, no `break`, no `continue`, no `return`.
- Strings and scalars captured from outside are copied, same as a lambda snapshot. Aggregates are read-only for the duration of the loop. The parent does not run during the loop, so the read-only rule is about the body, not about a concurrent parent.

The runtime splits the range into chunks of 8192 and pushes one task per chunk. 8192 is inside the plateau in section 3.5 (4096 and 65536 matched it; 256 did not). The chunk function is a direct indexed loop, compiled into the same module, with the bounds check hoisted once per chunk. It is not a callback per element. Section 3.6 is why.

There is no parallel reduction operator. A sum is `parallel for` into `ys[i]` and a serial sum afterwards, or it is a `spawn` tree of integer results. That keeps float addition order deterministic: the serial tail is the only reduction.

### 6.3 `spawn` and `join`

`spawn` applies only to a call. Arguments are evaluated on the parent, left to right. Each argument's type is a **value type**: `int`, `float`, `bool`, `char`, `string`, or a tuple / enum / `Option` / `Result` whose payloads are value types all the way down. Struct, Vec, HashMap, and closure arguments are a compile error in v0.4.0. The callee runs on a worker. `join` returns the value.

`string` is copied across the boundary (it already has value semantics). The child's copy and the parent's copy are different objects. No aggregate identity crosses a thread.

`Task<T>` must be joined on every path out of its scope, including early return. The check is the same shape as definite assignment. A dropped task is a compile error, not a detached thread.

`join` does not block the pool. The waiting worker takes tasks from its deque and steals until the child is done. A fixed pool in which every worker waits in `join` deadlocks; this rule is what prevents it. Nested `fib` was not benchmarked. The imbalance run in section 3.5 is the evidence that stealing matters; the join rule is a correctness requirement, not a measured speedup.

The oracle runs `spawn` by calling the function on the same thread and `join` by returning that value. `parallel for` runs as an ordinary loop. That matches the native runtime because section 6.4 makes the result independent of schedule.

### 6.4 Isolation

A function is isolated when all of the following hold:

- It does not call I/O or process builtins (`print`, file operations, `exec`, `exit`).
- It does not read or write a `var` global. A `const` of value type may be read.
- It does not mutate a struct, Vec, or HashMap, except for the single parallel-for index write when the function is the loop body.
- Every function it calls is isolated, including the callee of `spawn`.

The checker computes this. There is no user-written effect annotation. A violation is a normal type error with a source location. This is what makes a sequential oracle a valid implementation, and what makes data races a compile error rather than a memory model.

### 6.5 Pool

`rey_init` creates `REY_THREADS` workers if that variable is set, otherwise the logical CPU count. The pool lives until process exit. Creating threads inside a `parallel for` is what made the one-worker run slower than serial in section 3.5; the runtime does not do that.

Each worker has a Chase-Lev deque. The prototype's memory orders are the ones in Lê, Pop, Cohen, and Zappa Nardelli (PPoPP 2013): release publication of the task, a seq_cst fence between `top` and `bottom`, and a seq_cst CAS for the race on the last element. Indices are signed so an empty pop does not wrap. Tasks are a `{begin, end}` pair or a function pointer plus an argument block of value-type bits. The deque is bounded and power-of-two; overflow is a runtime error, not a silent resize, in v0.4.0 (the prototype aborts when full; a 65,536-slot deque held the 10^8-element run).

Workers sleep on a condition variable when the deques are empty and no collection is requested. The prototype spins; production should not, because this machine is shared and an idle spin is hostile. Idle-sleep latency was not measured.

### 6.6 Interaction with the collector

v0.4.0 tasks exchange values, not aggregate pointers, so no object is mutated on two threads. Reference counts are unnecessary on the thread boundary, and the ones we do not have do not need to be atomic. A string result of `spawn` is a new object allocated on the child and transferred by moving the pointer to the parent at `join`, after the child has finished. The transfer happens-before the parent reads it, because `join` synchronizes. The object stays on the shared heap; only the allocating thread bumps, and the receiving thread merely holds a root.

Stop-the-world collection, if it happens at all during a parallel region, waits for chunk boundaries. Numeric chunks do not allocate. A `parallel for` that builds strings will safepoint inside `rey_gc_alloc`.

## 7. Bit operations

These can land as soon as v0.3 stage 1 is green. They do not depend on sections 4–6.

### 7.1 Operators

On `int` only:

| Operator | Meaning |
|---|---|
| `~` | bitwise complement. `~0` is `-1`. No overflow check. |
| `&` `\|` `^` | bitwise and, or, xor. No overflow check. |
| `<<` | left shift. Vacated bits are 0. `1 << 63` is `-9223372036854775808`, the bit pattern with only the high bit set. This is not an arithmetic overflow. |
| `>>` | arithmetic right shift. `-1 >> 1` is `-1`. `-8 >> 1` is `-4`. |
| `>>>` | logical right shift. `-1 >>> 1` is `9223372036854775807`. `-8 >>> 1` is `9223372036854775804`. |

Shift count: if the count is `< 0` or `>= 64`, the program exits 1 with `error: shift count out of range`. Both operands are `int`, so a negative count is expressible and is an error, not a wrap. This is the same policy as checked division, and it is not C's undefined shift and not Java's masked count. A constant count in `0..63` has the check deleted at codegen. `<<`, `>>`, and `>>>` are not defined on `float`.

Compound forms `<<=`, `>>=`, `>>>=`, `&=`, `|=`, `^=` evaluate the left-hand side once, like the existing compounds.

### 7.2 Precedence

Highest to lowest. Assignment stays right-associative. Everything else listed here is left-associative.

| Level | Operators |
|---:|---|
| 1 | call, index, member, postfix `++` `--` |
| 2 | prefix `!` `~` `-`, prefix `++` `--` |
| 3 | `*` `/` `%` |
| 4 | `+` `-` |
| 5 | `<<` `>>` `>>>` |
| 6 | `&` |
| 7 | `^` |
| 8 | `\|` |
| 9 | `<` `<=` `>` `>=` |
| 10 | `instanceof` |
| 11 | `==` `!=` |
| 12 | `&&` |
| 13 | `\|\|` |
| 14 | `=` and every compound assignment |

`a & 1 == 0` parses as `(a & 1) == 0`. That follows Rust, not C. C's precedence makes that expression `a & (1 == 0)`, which is a standing trap. The bitwise operators are new, so there is no existing Rey program that depends on the C reading.

The lexer prefers the longer token: `>>>` before `>>` before `>`, and `>>>=` before `>>=`.

### 7.3 Methods

```rey
let bits = x.popcount();
let high = x.clz();
let low = x.ctz();
let below = x.ult(y);
```

`popcount`, `clz`, and `ctz` take `int` and return `int`. `clz(0)` and `ctz(0)` are 64, not a trap. `popcount(0)` is 0. `popcount(-1)` is 64. `clz(1)` is 63. `ctz(1)` is 0.

LLVM: `llvm.ctpop.i64`, and `llvm.ctlz.i64` / `llvm.cttz.i64` with the "zero is poison" argument false. `__builtin_clzll(0)` is undefined in C; the lowering must not be that builtin applied to a value that might be zero. The popcount lowering is worth it: section 3.6 measured 0.142 ns/element vectorized against 7.87 ns for a 64-step loop, and the object code contains `cnt.16b`.

`ult`, `ule`, `ugt`, `uge` compare the bit patterns as unsigned and return `bool`. They exist so that a mask with the high bit set has a defined order without a `u64` type. Signed `>` stays signed.

### 7.4 What is not added

No `u8`, `u16`, `u32`, `u64`, or `i32`. Each width needs conversions, an overflow rule, and literal suffixes. v0.3 already rejected `uint` and `byte`. Every bit pattern fits in `int`. The operations that actually need a second interpretation of those bits are logical shift and unsigned compare, which are `>>>` and the four methods.

No `bytes` type and no `[u8]`. A Rey string is already a byte sequence: it preserves `NUL` and invalid UTF-8, indexing returns one byte, and file I/O writes those bytes (`SPEC.md` §11). A mutable packed buffer would be one new reference type, which is less than five integer types, and it is still more surface than v0.4.0 needs. If a later profile shows `Vec<int>` at 8 bytes per byte dominating a real parser, add one `buffer` type then. Not now.

Stage 0 in section 9 is the operators, the three bit methods, and the four unsigned compares. That is the piece that is small enough to land immediately after v0.3 stage 1.

## 8. SIMD

No `simd` type, no lane width in the surface, no intrinsic module.

The C sum is already at 0.140 ns/element at `-O2`, which is about 57 GB/s of 8-byte loads. That is the memory-bandwidth region on this machine. A hand-written vector type does not make a bandwidth-bound sum faster, and it is a large surface (another family of types, an ABI, and a standard library). The gap that *is* measured is elsewhere:

- `-O0` is 6.9× slower than `-O2` on the same sum (0.961 vs 0.140).
- Turning vectorization off at `-O2` is 2.6× slower (0.366 vs 0.140).
- A per-element call is as slow as `-O0` (0.990 and 0.960).

So the compiler's job is to emit the shape LLVM already vectorizes:

- Counted `for` loops with a trip count in a register, which `parallel for` chunks are.
- The bounds check hoisted before the loop, or written inline against the loop bound so it deletes. A runtime call per index does not vectorize. v0.3's per-index `rey_vec_get` must not be inside a numeric chunk; codegen loads the data pointer once.
- `-O2` for user code. The compiler today is described as always `-O0` in the v0.3 handoff. That is a defect relative to this section, not a semantic freeze.
- No `fast`, `contract`, or `reassoc` on float instructions. Section 3.6 shows default clang contraction changes `0.1 * 0.1 - 0.01`. Rey codegen emits LLVM IR itself, so it emits `fmul` and `fadd` separately and does not set the `contract` flag. Passing `-ffp-contract=off` to clang matters for C fragments; it does not replace correct IR. Integer loops do not need fast-math, and float loops must not turn it on to chase a vector reduction.
- `noalias` only on the output buffer of a `parallel for`, and only because section 6.2 says that buffer is not read in the body. A normal Vec is a shared reference. Marking every Vec `noalias` would be a miscompile under the current value model.

Explicit vector types are worth reconsidering only after a self-hosted Rey program is more than about 2× slower than the C `-O2` kernel on the same algorithm for a reason other than bounds checks and per-element calls. That comparison has not been run, because Rey is not self-hosting.

## 9. Implementation plan

Each stage is independently testable. Later stages do not start by rewriting earlier ones. Line counts besides the prototypes are estimates.

| Stage | What | Where | Size | Done when |
|---|---|---|---|---|
| 0 | Bitwise operators, shifts, `popcount`/`clz`/`ctz`, unsigned compares | Rust lexer/parser/interpreter, Rey lexer/parser/checker/codegen. No allocator change. | estimate 400–700 lines across both engines | Conformance fixtures in section 7 match on both engines, including the numeric examples |
| 1 | `rey_buf_*` and point Vec/HashMap growth at `realloc` | C runtime only | estimate ~150 lines, plus call-site edits in `vec.c` and `hashmap.c` | Existing runtime tests pass; a growth test frees the old buffer; objects may still leak |
| 2 | Mark-region collector, shadow stack, safepoint between chunks | `gc.c` in the C runtime; codegen emits push/pop/poll; oracle unchanged | prototype `bench_gc.c` is 501 lines and has no threads, no large objects, and no real Rey layouts. Estimate 900–1,400 lines of C and 200–400 lines of codegen | C tests reproduce the ring, the pair, and "allocate, drop, allocate again." A native soak test finishes. Oracle behavior on cycles is unchanged |
| 3 | Pool, `parallel for` | C runtime plus checker and codegen. Oracle runs the loop serially | prototype `bench_steal.c` is 354 lines and creates threads per run. Estimate 500–800 lines of C and 400–700 lines of compiler | A program that writes `ys[i]` matches the oracle byte for byte. The chunk IR is a direct loop |
| 4 | `spawn` / `Task.join` for value types | Checker, codegen, C pool, oracle (eager call) | estimate 400–800 lines | `fib` of a small `n` matches the oracle. A task that is not joined is a type error. An aggregate argument is a type error |
| 5 | Comparison harness | scratch only, after self-host | not a language change | Section 10 has been run and the numbers are in a report |

Not scheduled, on purpose: unsigned integer types, a `buffer` type, channels, mutexes, explicit SIMD, region inference, atomic reference counts, a cycle collector, weak references, finalizers, moving collection.

Suggested order is the table order. Stage 0 does not wait for the collector. Stage 1 should land before stage 2 so that `free` in `vec.c` is already aimed at the buffer heap. Stage 3 does not require stage 2 for correctness of integer loops, but a `parallel for` that allocates strings does. Implement stage 3's integer-only body first, then string allocation once stage 2 exists.

The main memory-safety risk is a missing shadow-stack push. Mitigation: debug builds zero freed lines and check the tag on every traced pointer; the ring tests run under that mode. There is no separate test that proves every alloca was pushed. That remains a review item for the codegen stage.

## 10. Comparison harness, after self-host

Do not run this to claim a language ranking until the native compiler is self-hosting and the collector is in. The C numbers in section 3 are the baseline the Rey column has to sit next to. No other language was run.

Programs live in scratch, not in the Rey repo, so the repo gains no dependencies. Serial is the required column. Parallel is an optional column only where the language's standard library can express it without a third-party package.

Workloads, same algorithm, idiomatic code, no hand-written SIMD, no fast-math:

1. Sum 10^8 `int64` values. C baseline on this machine: 89 ms serial, 41 ms static 4-thread, 38 ms stealing 4-thread, RSS 801 MB. That C kernel is a mix hash, not a bare add; the bare `-O2` sum of 10^7 was 0.140 ns/element (section 3.6). Report both the bare sum and the mix, separately.
2. Write `ys[i] = xs[i] * xs[i] + xs[i]` over 10^8 elements. This is the `parallel for` shape.
3. Concatenate a one-character string 10^6 times, and, as a second number, build the same text with a pre-sized buffer. Rey's strings are immutable, so the naive loop allocates. Publishing only the naive number, or only the builder number, would be a rigged comparison.
4. Insert 10^6 short string keys into a HashMap and look them all up.
5. Build a binary tree of 10^6 nodes and a ring of 10^6 nodes, drop the roots, allocate the same structure again. Report peak RSS. This is the collector comparison. Languages that collect cycles will not grow without bound on the ring; a reference-counted runtime that does not collect cycles will.
6. Wall time of the Rey compiler checking its own source, once that exists. There is no paired program in the other languages. Report it alone.

Languages: C (`/usr/bin/clang -O2 -ffp-contract=off`), Rust (`--release`, standard library threads, no Rayon), Go (default compiler), Swift (`-O`, serial unless GCD is used, and GCD is then labeled as such), Python 3 (CPython, no extra JIT). Median of 5, peak RSS, same machine, nothing else claiming the cores if that is actually true at the time. It was not true for section 3.

## 12. Owner questions

These change the design if the answer is no.

1. Is it acceptable that the native runtime collects cycles and the Rust oracle, which uses `Rc`, does not? Observable behavior matches until a program runs out of memory.
2. Is the concurrency surface in section 6 acceptable: no I/O, no global `var`, no aggregate sent across a thread, oracle runs it sequentially?
3. Are `>>>` and `int.ult` acceptable substitutes for adding `u64` and the rest of the fixed-width integers?
4. Is compiling user programs at `-O2`, with float ops emitted as separate IEEE operations, acceptable? v0.3 has been emitting `-O0`.
5. Should a mutable packed `buffer` be a v0.4 goal, or do byte strings stay the only byte sequence until something measures a need?
