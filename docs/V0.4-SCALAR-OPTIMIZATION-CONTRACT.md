# Scalar analysis and folding, revision 1

These modules consume verified scalar/raw IR. They are groundwork for later
storage placement and root maps; they do not implement regions, promotion,
automatic roots or collection.

## Liveness

`ir::liveness::analyzeProgram(program)` returns
`Result<ProgramLiveness, string>`. Results retain function/block order and IDs.
Each block reports sorted unique value IDs in `liveIn`, `liveOut`, and
`liveAtTerminator`, plus `liveBefore`/`liveAfter` for each instruction index.
These are semantic liveness sets. `liveAtTerminator` is immediately before
the condition, return value and semantically required edge uses. `liveOut` is
the union of successor requirements after parallel substitution of live block
parameters with their corresponding edge arguments. Dead successor parameters
do not make their edge arguments live. Live block parameters remain in
`liveIn`; consumers must account for their definitions at block entry.

Every instruction operand is a use, even when its result is dead. Calls,
checked arithmetic and raw operations can have observable behavior. `RawFail`
is conservatively modeled as an ordinary operand use, so following values may
remain live. No instruction removal is authorized by this analysis.

Malformed IR fails verification. Sparse IDs are represented without allocating
an array up to the maximum ID. A deterministic one-million-unit work budget
bounds liveness analysis and snapshot construction after verification;
exhaustion returns an error, never partial liveness facts. The verifier's work
is outside this budget and includes block-count-squared tables, so this is
not a bound on the whole API's time or memory.

Future slot allocation must also account for actual emitted writes. Current
backends write every formal parameter and every target block parameter,
including dead ones. Sharing these locations using semantic liveness alone
would overwrite live values. No slot reuse is enabled in this slice.

## Constant folding

`ir::optimize::scalar::foldConstants(program)` returns
`Result<IRProgram, string>`. It verifies both input and output and constructs
independent mutable IR nodes and vectors. The input remains unchanged.

Known i64/bool constants are tracked within each block by SSA ID. Safe checked
addition, subtraction, multiplication, division, remainder, integer comparisons
and boolean equality/inequality become canonical constants. Result IDs, types
and source spans are preserved. Potential overflow, division by zero and
`INT64_MIN / -1` or `% -1` retain the original instruction at its original
position. Compile-time calculation must check safety before doing arithmetic
in the historical seed.

The pass preserves every instruction, block, edge, call and raw operation in
order. It does not propagate between blocks, infer call results, read memory,
remove constant definitions, simplify branches or perform dead-code removal.
Immutable scalar constants remain known across calls. Effects do not prove
that a checked operation or call cannot trap or diverge.

## Experimental drivers

Both `rey-compiler/ir-main.rey` and `native-main.rey` accept an optional trailing
`--fold-constants`. It may precede or follow `--std-root <directory>`. Duplicate,
unknown and missing-value options (including an empty std root) fail with
status 2. A relative directory whose name begins `--` can use a `./` prefix.
Folding is off by default
so evaluation, diagnostics and emitted execution can be compared independently.

This option applies only to the experimental direct native pipeline; it is not
a change to the installed v0.3.1 CLI. Correctness evidence must include folded
and default execution, retained runtime errors, actual transformed IR and
source/module boundaries. Pass existence or smaller code is not a runtime or
compile-time speed measurement.
