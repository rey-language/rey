# First native scalar backend contract

This bring-up slice consumes verified scalar IR. It is not a complete v0.4
compiler/runtime and has no managed allocation, containers, tasks, or collector.
The historical seed may build its implementation. Executables emitted by the
new backend must contain machine instructions and OS calls emitted in Rey,
with no compiled C implementation of the Rey runtime and no compiler subprocess,
assembler, or external build linker.

Production arm64 macOS requires its dynamic OS loader. Its dyld startup also
requires the OS-provided libSystem image. Emit the corresponding load commands
in Rey; these OS startup components are distinct from the Rey allocator,
collector, strings, containers, and compiler. No Rey C runtime archive or
imported C allocation implementation is part of this native slice. A claim
that the macOS executable loads no C-based system library would be inaccurate.

## Exclusive module boundaries

`native/bytes` provides validated unsigned byte encoding and pure Rey SHA-256:

```text
byteString(bytes: Vec<int>): Result<string,string>
appendU32Le(bytes: Vec<int>, value: int): Result<bool,string>
appendU32Be(bytes: Vec<int>, value: int): Result<bool,string>
appendU64Le(bytes: Vec<int>, value: int): Result<bool,string>
patchU32Le(bytes: Vec<int>, offset: int, value: int): Result<bool,string>
sha256(bytes: Vec<int>): Result<Vec<int>,string>
```

All unsigned values must fit their specified width. `appendU64Le` initially
accepts nonnegative signed-64 values, sufficient for image offsets/addresses.
SHA-256 returns exactly 32 digest bytes in standard big-endian digest order.
Input bytes outside 0..255 and invalid patch ranges are errors. Mutation of the
destination Vec is explicit; SHA-256 and byteString do not mutate input.

`native/arm64` provides:

```text
NativeFunctionOffset { functionId: int, offset: int }
Arm64Code { bytes: Vec<int>, entryOffset: int,
            functions: Vec<NativeFunctionOffset> }
emitArm64(program: IRProgram, targetOS: string): Result<Arm64Code,string>
```

OS names are `darwin` and `linux`; other names fail explicitly. Function offsets
and entryOffset are byte offsets into the returned code. Code is position
independent within one contiguous executable text area. Resolve all internal
calls, branches, and overflow traps before returning. No external relocations.

The entry stub calls the program entry function and exits through the target
OS syscall. A void result exits zero; scalar result uses the low exit-status
bits. Checked addition overflow exits 1 (the SPEC.md runtime-error status) in this first executable slice.
The evaluator remains the source-context diagnostic oracle until native
diagnostic output is implemented. This behavior must be documented/tested.

Use AArch64 x0..x7 for the first eight machine arguments and stack slots for up
to eight additional arguments, x0 for a scalar result,
x9..x15 as scratch, and preserve SP alignment and x29/x30 across calls.
Start with per-SSA-value frame slots and a separate edge scratch area; block
arguments must transfer in parallel, including loops and swaps. No source
optimization is implied by this baseline emitter. Explicitly reject more than
sixteen arguments, unsupported frame sizes, unrepresentable branch offsets, and
any unsupported IR. Never truncate an encoding or silently emit another op.
The current ARM64 frame cap is 32768 bytes. Larger SP adjustments are split
into aligned chunks of at most 4080 bytes; frame accesses must fit the scaled
load/store offset limit of 32760 bytes. Hidden managed parameters count toward
the sixteen-machine-argument limit. The argument gate covers 8/9/10/16 arguments,
hidden pointers, a 9600-byte frame, and rejection at 17 arguments.
Literal construction must handle the whole signed-64 domain without negating
INT64_MIN. Sparse SSA IDs must not directly determine stack allocation size.

`native/image` provides:

```text
buildMachOArm64(code: Arm64Code): Result<Vec<int>,string>
buildElfArm64(code: Arm64Code): Result<Vec<int>,string>
```

The image owns headers, load commands, layout/alignment, entry addresses, and
any required embedded ad hoc Mach-O code signature. It does not invoke system
tools to assemble, link, or sign. Use the bytes/SHA module for binary encoding
and hashing. Darwin execution is the first host acceptance gate; Linux images
are structurally checked until an actual AArch64 Linux runner is available.
Host-side test scripts may inspect/disassemble and set executable permission.
Those bring-up test steps do not establish a production filesystem API.

On Darwin arm64, use `MH_DYLDLINK | MH_PIE`, the system dyld/libSystem load
commands, and an `LC_MAIN` entry. Static `LC_UNIXTHREAD`-only images are rejected
by production arm64 kernels and do not satisfy the execution gate. OS loader
startup is permitted; externally invoking a build linker remains prohibited.

## Gate before expanding the backend

Run actual Darwin arm64 binaries for literals, calls, branches, comparison
predicates, signed extrema, checked overflow, recursion within a declared
bound, and parallel block arguments. Compare exit status with IR evaluation.
Inspect instructions and embedded signature/image bounds. Capture exact source
and executable hashes. An emitted file or successful build alone is not a
native execution result. Full source-language parity, stack guard behavior,
managed runtime support, Linux execution, and remaining platforms remain gates.

Format references: the installed Apple SDK's `mach-o/loader.h` and
`mach/arm/thread_status.h`, and Apple's
[CodeDirectory definitions](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/cs_blobs.h).
The platform requirement is specified by
[XNU's static/dynamic loader checks](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/mach_loader.c)
and [dyld's libSystem/entry checks](https://github.com/apple-oss-distributions/dyld/blob/main/dyld/dyldMain.cpp).
These define the executable/signature formats; actual host execution remains
the acceptance evidence for emitted files.

## Linux x86-64 scalar extension

`native/x64` provides `X64FunctionOffset { functionId, offset }`,
`X64Code { bytes, entryOffset, functions }`, and
`emitProgram(program: IRProgram, target: string): Result<X64Code,string>`.
The supported target is `linux-x64`; Windows and Darwin x64 remain explicit
unsupported targets. The SysV calling convention supports six register
arguments and up to ten stack arguments, an aligned stack, and an RAX result.
All current checked scalar operations and parallel block transfers are encoded
directly in Rey. Frame size is capped at 65520 bytes; more than sixteen arguments
and unrepresentable branches fail explicitly.

`native/image/x64` provides `buildElfX64(code: X64Code)` returning image bytes.
The ELF64 writer emits an x86-64 executable with a read/execute load segment
and an explicit non-executable stack. Unlike AArch64, instruction offsets need
not be four-byte aligned. It imports no runtime and uses no external linker.
Format references are the [ELF header](https://gabi.xinuos.com/elf/02-eheader.html)
and [program header](https://gabi.xinuos.com/elf/07-pheader.html) definitions.

The x64 byte/image gate and 64 source program executions pass, plus two
hand-built IR executables covering recursion and eight-argument calls. These
executions use x64 emulation in the available ARM64 Linux VM. They do not
establish a native x64 hardware/platform release gate. Execution caught a
division-guard branch erroneously retargeted to the overflow handler; the
encoder and a specific structural regression assertion now preserve that
guard's local continuation. Evidence is recorded in the parallel ledger.

## Trusted ARM64 raw-memory extension

Darwin/Linux ARM64 additionally implement the internal raw operations in
[V0.4-RAW-MEMORY-CONTRACT.md](V0.4-RAW-MEMORY-CONTRACT.md), using emitted OS
mapping syscalls and aligned native memory instructions. Address cells remain
typed separately from integer/byte data. The evaluator verifies their
provenance; the native runtime caller must satisfy the documented ownership
and memory-extent preconditions. Ordinary source checking grants no raw
authority, and no public CLI flag changes that. These primitives passed 32
real executions on each ARM64 OS. They do not implement managed references,
automatic collection, region inference or a raw x64 runtime.
