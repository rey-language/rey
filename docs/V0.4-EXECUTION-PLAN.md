# Rey v0.4 execution plan

Status: implementation proposal, 2026-10-21. No milestone below is implemented or verified by the act of writing this plan.

This is the forward plan for the pure Rey native compiler and automatic memory management discussed with Misbah. It supersedes conflicting architectural choices in [V0.4-DESIGN.md](V0.4-DESIGN.md). Changes to language behavior must still be specified in [SPEC.md](../SPEC.md) and tested before implementation is accepted.

## 1. The outcome

Ship a compiler, optimizer, native backend, executable writer/linker, and Rey runtime implemented in Rey. A distributed native Rey compiler must compile programs and rebuild the compiler/runtime without invoking or loading Clang, LLVM, a C compiler, an external assembler/linker, Zig, Cargo, or Rust.

The execution pipeline is:

```text
source -> checked program -> typed control-flow IR -> memory analysis
       -> optimization -> target instructions -> register allocation
       -> encoded instructions -> executable and debug metadata
```

The memory strategy is:

1. Eliminate objects whose identity/storage is unobservable.
2. Use registers and suitable stack storage for local values.
3. Infer regions for allocations whose collective lifetime is established.
4. Construct escaping results in their destination when possible.
5. Use a tracing heap when sharing or lifetime cannot be established statically.

Capy remains the normal entry point for builds, runs, checks, diagnostics, packages, and updates. The compiler owns dependency-aware incremental compilation; Capy forwards project inputs and presents the results.

## 2. What pure Rey means

- Production compiler and runtime implementation sources are Rey. Machine instructions are emitted by code written in Rey, including the implementation of compiler-recognized intrinsics.
- Operating-system APIs, system dynamic libraries, and platform ABIs remain permitted dependencies. Calling an OS function through its ABI does not require a C compiler. Record all such dependencies per target.
- Low-level code needs a small trusted primitive layer: raw loads/stores, pointer arithmetic, exact-width bit operations, alignment, target calls, and atomic operations with specified ordering. Add these deliberately to the internal language/runtime contract. Ordinary packages must not gain implicit access to trusted operations.
- The production compiler must not hide an LLVM library, translate through C, invoke a system linker, or silently fall back to the legacy toolchain.
- The historical v0.3.1 compiler is a recorded bootstrap seed only. Its historical C/LLVM dependency is permitted during initial bring-up; it must not enter the final runtime or become necessary for ordinary builds or native self-rebuilds.
- Existing bootstrap/reference tooling can remain available for differential checks. It is not a production v0.4 implementation dependency.

This explicitly revises the old proposal's LLVM backend, C-only runtime work, and exclusion of low-level operations needed to implement a native toolchain. It does not imply public unsigned types, unrestricted unsafe user code, or a changed object model without a separate specification decision.

## 3. Semantic constraints

Preserve v0.3 observable behavior unless a versioned specification change explicitly replaces it:

- Structs and collections share mutable identity. Allocation elimination, moves, and representation changes must preserve equality and every observable alias.
- Closures snapshot scalar values and share reference aggregates as specified.
- Signed integer overflow remains a checked error. Floating-point operations retain specified rounding, evaluation order, and contraction behavior. No fast-math or undefined overflow assumptions to improve a score.
- Preserve short-circuiting, side-effect order, validation, runtime errors, and diagnostics.
- Cycles remain supported. A cycle wholly contained in a dead region can be reclaimed together; cycles with uncertain external reachability belong on the managed heap.
- A returned pointer, stored field, captured value, global assignment, task transfer, or opaque call can extend a lifetime. Incomplete analysis must select safe storage, not assume that a value is local.
- Fusing a parser with a consumer must not skip required validation of unused fields or reorder observable failures. Restrict transformations to established equivalences.

## 4. Current starting point

- The native frontend and LLVM emitter live under `rey-compiler/` and are written in Rey.
- [codegen/main.rey](../rey-compiler/src/codegen/main.rey) lowers checked source to LLVM text and invokes native compilation tools.
- [runtime/mem.c](../rey-compiler/runtime/mem.c) allocates and zeroes objects without general reclamation. Growable buffers have separate ownership/reallocation behavior that the new manager must preserve correctly.
- [runtime/string.c](../rey-compiler/runtime/string.c) tracks string pointers in a growing membership table. That table is not string-content interning and must not accidentally keep every string alive in the new collector.
- [build-release-target.sh](../scripts/build-release-target.sh) currently bootstraps with Rust and builds a C runtime. It must eventually be replaced for v0.4 release construction.
- Capy currently invokes the compiler as a subprocess; its packaging assumes `bin/runtime/librey_rt.a`. New packaging needs an explicit versioned layout rather than a file renamed to impersonate that archive.
- Published platform coverage is macOS arm64/x86-64, Linux arm64/x86-64, and Windows x86-64. Keep all five as final release targets.

The saved performance CSVs are historical observations, not v0.4 forecasts or verified measurements of every currently published binary.

## 5. Milestones, in dependency order

### M0. Establish a reproducible baseline

Work:

- Record the source commit, compiler/runtime/std hashes, compiler seed, machine, OS, CPU, memory, build options, and package provenance.
- Recheck language conformance, native frontend fixtures, runtime behavior, and compiler bootstrap against the current source. Record actual passes/failures; do not import historical pass counts as current evidence.
- Audit the actual seed's capabilities before backend work: exact-length binary I/O, embedded NUL/all 256 byte values, byte packing, supported compiler-source syntax, and usable stdlib interfaces. Source inspection alone does not establish the published seed's behavior. A missing seed capability must get an explicit bring-up route before its dependent milestone starts.
- Repair correctness blockers before treating timings as optimization baselines.
- Extend the comparison harness to build equivalent single-workload programs for C, C++, Rust, Zig, Go, Python, direct Rey, and Capy. The existing shared multi-workload competitor builds are not equivalent to Rey's separate program builds.
- Add representative allocation-heavy cases: escaped closures, request parsing with retained output, cyclic graphs, compiler-like AST passes, growing collections, and repeated request processing.
- Measure process startup independently and make workload bodies long enough for meaningful timing. Record execution, clean build, no-op build, incremental edit, peak RSS, live managed bytes, reserved bytes, allocation count, and copied payload bytes separately.
- Supply sizes/data at runtime consistently. Validate outputs independently, including processed-item counts and error cases. A matching checksum alone does not prove equivalent work or semantics.

Exit: reproducible raw results and known semantic failures, with a documented comparison method and no unsupported language-ranking claim.

### M1. Add a typed intermediate representation

Proposed code: `rey-compiler/src/ir/` and `rey-compiler/src/analysis/`, connected to the checked frontend in `rey-compiler/main.rey`. These directories are planned, not existing implementations.

Work:

- Represent typed values, basic blocks, branches, calls, checked arithmetic, allocations, fields, indexed accesses, copies, captures, and returns explicitly. Use SSA values/block parameters where appropriate.
- Track pointer-containing values and nominal layouts separately from integer payloads, including erased containers and enum variants.
- Preserve source spans and stable function identities for diagnostics, debugging, caching, and optimization explanations.
- Add an IR verifier for operand/result types, dominance, control flow, layouts, checked operations, and initialized values.
- Implement a small IR evaluator in Rey for deterministic differential checks during backend bring-up.
- Produce conservative per-function summaries: reads/writes, escaping arguments/results, allocation, blocking, synchronization, and unresolved callees. Recursive call groups require fixed-point summaries with bounded analysis effort.

Exit: representative source programs lower to verified IR and agree with reference behavior. Unknown effects are explicit. No new LLVM optimization dependency is introduced.

### M2. Bring up direct native code and a minimal Rey runtime

Proposed code: `rey-compiler/src/backend/`, `rey-compiler/src/object/`, `rey-compiler/src/link/`, and `rey-compiler/runtime-rey/`.

First target: macOS arm64, allowing native execution and debugging on the current development host. Implement target details behind interfaces so the other platforms do not fork language semantics.

Work:

- Implement trusted runtime intrinsics as native instructions/ABI calls. Define their typing, alignment, aliasing, and initialization rules.
- Select ARM64 instructions from verified IR. Implement register allocation, spills, stack frames, argument/result passing, relocations, and calls.
- Emit Mach-O executables and resolve required system-library imports. Handle platform-required executable metadata/signatures in the writer; normal compilation cannot quietly invoke an external assembler, linker, or signing tool.
- Use append-oriented byte buffers and explicit endian encoders with tested bounds/relocations. Avoid constructing large executable images through repeated immutable string concatenation. Verify byte-for-byte file output, including embedded zero bytes.
- Start with entry/exit, arithmetic, branches, and OS-backed I/O; expand to exact floating-point behavior, aggregates, containers, indirect calls, closures, modules, and error paths needed by compiler source.
- Implement the minimal runtime in Rey: startup, failure reporting, raw memory primitives, strings, collection operations, and OS interfaces. A temporary bounded bump allocator is bring-up code only, not the release memory manager.
- Keep the new compiler's implementation within seed-supported Rey syntax until the new backend can compile any extensions it starts using. New runtime syntax is input to that compiler and need not be executable by the old seed directly.

Exit: representative programs execute using direct machine code and a Rey runtime; generated programs contain no linked Rey C runtime. Inspect instructions/imports and trace subprocesses. Primitive conformance, ABI, relocation, and malformed-output checks pass.

### M3. Implement correct automatic reclamation

Work:

- Implement an initially non-moving tracing heap in Rey, with a thread-local allocation fast path, explicit safepoints, type/layout descriptors, and precise roots.
- Use a shadow-stack root protocol for bring-up. Model roots in IR so later liveness improvements can shorten retention. Enumerate globals, native runtime temporaries, closures, interior string pointers/views, and collection buffers explicitly.
- Define how native registers/spills reach the root set at every safepoint. Collector entry cannot lose a pointer held only in a register or a runtime helper.
- Keep raw buffer storage under explicit internal ownership. Trace reference-bearing elements; reclaim a dead owner's buffer once. Never interpret arbitrary integer elements as heap pointers.
- Remove or redesign the legacy string pointer table. A pointer-membership index must not become a strong root for all historical strings.
- Recycle small-object blocks and separately manage large/growable buffers. Trim surplus capacity according to an explicit policy; report live, reserved, and resident memory separately.
- Avoid recursive reclamation that overflows the stack. Collector work storage and failure handling must not recursively trigger allocation/collection.

Exit: shared objects survive; unreachable cycles are reclaimed; buffer ownership is correct; repeated requests reach a memory plateau; stale pointers, double reclamation, and root-loss cases fail verification. Use debug poisoning and forced collection at safepoints in the new runtime. Existing C sanitizers remain useful for reference components, not proof about the Rey runtime.

### M4. Close the native self-hosting loop

Bootstrap sequence:

1. **S0:** pinned v0.3.1 native seed plus recorded historical dependencies.
2. **H:** compile the new compiler's seed-compatible source using S0. H may still run on the old runtime, but it implements the new direct backend.
3. **S1:** H compiles the new Rey runtime and compiler with that backend. S1 is the first fully native compiler running on the Rey runtime.
4. **S2:** S1 rebuilds the runtime and compiler without the historical toolchain.
5. **S3:** S2 repeats that build. Require reproducible S2/S3 output under fixed inputs/options; remove nondeterministic paths, timestamps, identifiers, and section ordering instead of ignoring arbitrary differences.

Work:

- Complete every supported language/runtime operation used by the compiler itself.
- Run the current native conformance and compiler fixtures against S2/S3.
- Rebuild and run in a clean environment with Clang/LLVM/Rust/Zig and external assembler/linker tools unavailable. Trace process execution, dynamic-library loading, and binary imports; hiding tools on PATH alone is insufficient.
- Record bootstrap seed hashes and make each intermediate artifact's origin explicit.

Exit: independently rebuilding, behaviorally verified S2/S3 compilers and runtimes. No legacy C runtime objects, LLVM libraries, or compiler-tool subprocesses enter the production dependency closure.

### M5. Add escape analysis, stack placement, regions, and promotion

Implement in this order; each optimization has an off switch for differential comparison.

1. **Scalar replacement:** eliminate objects only where identity and aliases are unobservable. Preserve initialization, checked operations, side effects, and errors.
2. **Stack placement:** establish that every reference dies within a valid stack lifetime. Respect size limits, recursion, address stability, exceptions/errors, and safepoint root requirements.
3. **Region inference:** group allocations by an established common lifetime, such as an iteration, parser phase, or request. A function-wide arena is insufficient for a long-running loop. Before reset, establish that no surviving reference or collector root can reach the region.
4. **Destination construction:** pass a hidden result destination/region where the caller and callee can establish a valid lifetime and layout. Construct returned aggregates there directly. Cache only a bounded number of lifetime/layout specializations.
5. **Runtime promotion where necessary:** preserve graph identity, aliases, cycles, and every reference crossing the boundary. A moving promotion needs a complete update/forwarding protocol; otherwise select longer-lived storage before allocation. Do not retain a whole scratch region just to preserve one small survivor without reporting that retention.

Region data can reference a longer-lived managed object; that reference must participate in the root protocol until the region dies. A longer-lived managed object cannot keep an untracked reference into a reset region.

Exit: zero heap allocations for eligible local-object/closure cases; bulk reclamation for established region lifetimes; correct escaped results; bounded scratch retention across loops. Exercise aliases, cycles, containers, global stores, opaque calls, recursion, early returns, and task boundaries. Optimized/unoptimized results and failure behavior agree.

### M6. Optimize data movement and useful native code

Work:

- Add constant propagation, dead-value elimination, range analysis, bounded inlining, specialization, loop simplification, and bounds-check elimination when established by analysis.
- Remove redundant zeroing only when every potentially observed byte is initialized before a read, GC scan, or external call. Preserve required zero initialization and object metadata.
- Fuse a restricted set of collection/stream operations with known effects. First vertical slice: incremental CSV parsing, pure filtering, and checked integer aggregation.
- Use borrowed field views only where lifetime is established. Retained fields receive owned storage. Specify behavior for records crossing buffers and oversized input fields.
- Require parser validation/error behavior to match the unfused form. Do not reorder floating-point reductions or checked integer operations without an explicit semantic allowance.
- Add SIMD/parallel transformations only when legality and a useful granularity are established. Parallel execution must define errors, cancellation, worker roots, and deterministic results where promised.
- Defer broad automatic layout changes and CPU/GPU dispatch until this CPU vertical slice succeeds. Keep future layout planning possible in IR.

Exit: a normal modular pipeline lowers to a verified streaming implementation with no eligible per-row heap allocation or intermediate collections. Report actual runtime, payload copying, allocation, memory, code size, and compiler cost against matched implementations.

### M7. Make the compiler and Capy incremental

Work:

- Cache parsing/checking, function IR, summaries, native objects, and link results using hashes of source, transitive dependencies, compiler/runtime ABI, target features, semantic flags, and optimization settings.
- Invalidate callers when changed effects, layouts, inlined bodies, or generated specializations affect them. A source-text cache alone is unsound.
- Provide atomic cache writes, concurrent-build isolation, corruption detection, bounded size/pruning, and deterministic rebuilds. Cache failure falls back to a normal rebuild without accepting stale output.
- Implement no-op and function-edit builds. Report time through Capy's process startup and final executable creation; phase timings are additional data.
- Add a proposed `capy explain` interface for allocation placement, promotion, retained regions, unresolved effects, and prevented optimizations. Clearly distinguish established facts, conservative estimates, and measured observations.
- Add opt-in resource contracts incrementally: begin with no-heap-allocation and no-blocking properties over known callees. Diagnose the responsible call path. Foreign/opaque functions need trusted declared summaries or remain unknown.

Exit: dependency edits invalidate the right artifacts; clean/incremental outputs agree; stale/corrupt caches cannot change behavior; Capy presents measured build phases and truthful explanations.

### M8. Complete all release platforms and concurrency safety

Work:

- Share the typed IR and memory analyses across both instruction sets. Implement separate ARM64/x86-64 lowering and Mach-O/ELF/PE executable/object handling with the required relocations, imports, calling conventions, stack/unwind information, and loader metadata.
- Validate macOS arm64/x86-64, Linux arm64/x86-64, and Windows x86-64 on native runners. Cross-output generation is useful but not proof of native execution or installer behavior.
- Define task ownership before enabling shared mutable execution. Local regions use ordinary stores; exclusive task handoff uses the required synchronization. Shared state requires a specified synchronization policy.
- Implement safepoint coordination, shared roots, promotion/handoff rules, and required pointer-write barriers for the selected collector/concurrency design. Atomic reference counts alone do not make object fields race-free.
- Exercise failure paths, cancellation, worker exit, region teardown, and collection during task handoff. Avoid a global atomic/lock on every scalar write.

Exit: each platform independently builds, runs the language/runtime gates, self-rebuilds, and passes Capy installation/package checks. The required task/concurrency surface has a documented and verified memory model.

### M9. Package and publish v0.4

Work:

- Version the compiler/runtime package contract and update Capy's toolchain validation, installer, doctor, update manifest, and package-manager metadata.
- Stop requiring Clang/Xcode compiler tools for normal v0.4 use. List remaining OS/library requirements accurately. Do not remove legacy-install support before validating migration.
- Publish source provenance, seed hashes, native bootstrap evidence, platform coverage, semantic changes, benchmark raw data, and known limitations.
- Keep all five platform release assets gated on their actual build, runtime, bootstrap, and package results.

Exit: the hard release conditions in section 8 pass. The release notes explicitly resolve achieved and unmet performance targets. There is no claim of being faster than every language on every task.

## 6. Performance scorecard

These are engineering targets. No nanosecond allocation measurement establishes application runtime or compilation latency.

- **Core native execution:** aim for suite geometric-mean execution time at most 1.10 times the fastest matched C/C++/Rust/Zig implementation selected per workload. Report individual results; a geometric mean cannot hide a broken workload. Investigate every greater-than-10% regression against the corrected v0.3.1 baseline.
- **Allocation-heavy applications:** target at least 2x current Rey throughput at equivalent work and semantics. A 5x result on selected allocation/copy-heavy paths is a stretch target and must name those paths. It is not a multiplier for all benchmarks or a claim against tuned C.
- **Memory:** repeated fixed-size work must reach a plateau after warm-up, with retained outputs and maximum concurrency stated. Target peak RSS within 1.25 times manually managed C for matched, memory-dominated workloads. Report absolute RSS plus managed live/reserved bytes and distinguish baseline runtime overhead.
- **Small clean build:** target at most 100 ms through Capy on a declared reference machine and fixed project. Record development and optimized builds separately; preserve semantic behavior in both.
- **Small incremental edit:** target at most 50 ms through Capy for a declared one-function edit. Report no-op builds separately. Single-digit milliseconds are an experiment for specific cached/tiny cases, not a general release promise.
- **Compiler self-build:** record wall time and peak RSS for the same compiler source at fixed optimization/target settings. Establish its target after M0; do not invent a self-build duration from small-program timings.

Use C, C++, Rust, Zig, Go, and Python as the comparison set, with direct Rey and Capy overhead recorded separately. Keep CPU-kernel, allocation, streaming/I/O, concurrency, build, and startup results distinct. Python native-library workloads need a separate category.

## 7. Measurement protocol

- Fix algorithms, input data, integer widths, overflow policy, validation, output, thread count, and optimization modes. Document unavoidable differences instead of silently changing semantics.
- Compile one equivalent program/project per comparison. Do not compare an optimized single-file Rey program with a competitor binary containing unrelated workloads.
- Use an explicitly named reference host, record toolchain versions/options and artifact hashes, and check power/thermal/load conditions. Benchmark separately on ARM64 and x86-64 before portability claims.
- Begin with at least two warm-ups and nine measured runs; report medians and dispersion with raw samples. Increase workload length/repetitions when noise or startup dominates rather than reporting tiny differences as wins.
- Separate cold build, cached build, no-op build, one-function edit, process startup, and steady-state execution. Never label an in-process compiler phase as end-to-end Capy latency.
- Verify successful output, expected failures, input consumption, and meaningful work. Measure realistic retained outputs and long-running workloads; a process-exit-only benchmark cannot validate reclamation.
- Use allocation counters, copied-byte counters, root/region accounting, and instruction inspection alongside time/RSS. Instrumented runs are separate from headline timing runs.
- Compare optimizations individually enabled/disabled and all together. Speedup factors do not multiply automatically when they remove the same work.

## 8. Hard release conditions

1. Production compiler/runtime sources and native code generation are Rey; executable generation has no hidden external compiler/backend/linker dependency.
2. Every advertised language feature has current conformance evidence, including checked arithmetic, aliases, captures, and error behavior. Resolve inherited blockers before release.
3. Precise roots, cyclic reclamation, owned buffers, region reset, promotion, and concurrency boundaries pass targeted checks and repeated-work memory tests.
4. S2/S3 native bootstrap is reproducible on supported targets under a documented deterministic build configuration.
5. All five native release platforms pass build/run/bootstrap and Capy package/install gates.
6. Cache invalidation is correct, ordinary code cannot access trusted primitives accidentally, and optimization does not bypass semantics.
7. Publish a measured scorecard with unresolved performance regressions and target shortfalls explicitly resolved in release acceptance. Aspirational numbers are never presented as observations.

## 9. First implementation slice

Start M0, then the smallest M1 vertical slice. Do not begin by changing allocators or writing five backends in parallel.

The first compiler change should lower integers, locals, checked addition, calls, branches, and returns to verified typed IR, evaluate that IR, and emit an explanation of any allocation/effect facts. Add cases that distinguish overflow and branch/side-effect behavior from a merely matching happy-path result. Expand this slice to native ARM64 output in M2.

Each subsequent change names its milestone, touched interfaces, expected semantic behavior, required verification, and measurement artifact. A milestone is complete only when its exit condition has current evidence.

## 10. Research inputs

These are related work, not evidence that Rey already implements the ideas or that the combination is novel:

- [Perceus](https://www.microsoft.com/en-us/research/publication/perceus-garbage-free-reference-counting-with-reuse-2/): precise reference counting, reuse, and specialization. Study its resource reasoning without assuming its functional semantics match Rey's shared mutation.
- [MLKit](https://elsman.com/mlkit/): inferred regions combined with tracing collection.
- [Go collector guide](https://go.dev/doc/gc-guide): escape analysis and scoped storage alongside automatic collection.
- [MemOIR](https://mcmichen.cc/memoir/): collections represented independently of memory layout.
- [Futhark fusion](https://www.futhark-lang.org/blog/2026-03-24-scan-scatter-fusion.html): combining modular operations to remove intermediate data.
- [Resource Aware ML](https://www.raml.co/): inferred resource bounds for an analyzable language subset.
- [Zig native backend experience](https://ziglang.org/download/0.15.1/release-notes.html#x86-Backend): compilation-speed gains and generated-code tradeoffs when bringing up an independent backend.
