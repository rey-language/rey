# Trusted raw-memory bring-up, revision 2

The primitive gate passes 145 checks including 32 Darwin arm64 and 32 Linux
arm64 executions; see the parallel ledger. This is not an implemented
allocator, collector, region system, or user-facing unsafe API.
The coordinator owns revisions. It supplements [the managed memory
ABI](V0.4-MEMORY-ABI.md); a raw address is never a managed reference.

## Authority and types

Introduce an internal checker type `RawAddress` and IR type `raw.address`.
Its source spelling, `__rey_raw_address`, is accepted only in runtime units
explicitly authorized by the compiler. Do not infer authorization from a
filename, module name, import spelling, or source declaration. The ordinary
source-checking API authorizes no units. An internal checking API receives an
explicit list of source-unit identities from its caller. The production driver
will construct that list from its own bundled runtime; no CLI option grants
arbitrary packages authority. During bring-up, fixtures call the internal API.

An unauthorized unit cannot name this type, invoke raw intrinsics, or call a
function whose signature exposes it. There is no integer/address conversion,
`any` conversion, serialization, implicit dereference, or managed-reference
conversion. Raw values may be local SSA values, function arguments/results,
and block parameters within authorized code. Raw-address equality is explicit.
Descriptor/root integration arrives with managed references, separately.

## Primitive semantics

The initially supported targets are Darwin arm64 and Linux arm64. The runtime
source uses the following reserved intrinsic names; the checker records a
distinct intrinsic identity, and lowering must use that identity rather than
matching user function names.

| Source intrinsic | IR instruction | Operands | Result |
| --- | --- | --- | --- |
| `__reyRawNull()` | `RawNull` | none | raw.address |
| `__reyRawMap(size)` | `RawMap` | i64 | raw.address |
| `__reyRawUnmap(base, size)` | `RawUnmap` | raw.address, i64 | void |
| `__reyRawOffset(base, offset)` | `RawOffset` | raw.address, i64 | raw.address |
| `__reyRawLoadI64(address)` | `RawLoadI64` | raw.address | i64 |
| `__reyRawStoreI64(address, value)` | `RawStoreI64` | raw.address, i64 | void |
| `__reyRawLoadByte(address)` | `RawLoadByte` | raw.address | i64 |
| `__reyRawStoreByte(address, value)` | `RawStoreByte` | raw.address, i64 | void |
| `__reyRawEqual(left, right)` | `RawEqual` | raw.address, raw.address | bool |
| `__reyRawLoadAddress(address)` | `RawLoadAddress` | raw.address | raw.address |
| `__reyRawStoreAddress(address, value)` | `RawStoreAddress` | raw.address, raw.address | void |

- Map reserves anonymous private read/write, non-executable OS memory. Its
  positive byte length is checked before the OS call. Failure exits with the
  existing runtime-error status 1. Successful memory is initially zero.
- Unmap requires the original mapping base and the original positive requested
  length. The runtime owns that pairing and releases it once. Check OS failure;
  the kernel accepting a second unmap is not evidence that double release is
  valid. No collecting operation is invoked by these primitives.
- Offset accepts a non-null base and a nonnegative offset. Check addition for
  overflow and require a nonnegative user address. The runtime caller must
  establish that the derived address stays inside the live owned mapping.
  This primitive alone does not implement object bounds or lifetime checking.
- Loads/stores require live, readable/writable memory of sufficient extent.
  Eight-byte accesses require eight-byte alignment. Byte stores validate the
  value is in 0..255 before narrowing. Violations of dynamic numeric/alignment
  checks exit 1; arbitrary unmapped dereferences remain a trusted-code bug.
- Raw equality compares exact addresses, including null. It does not inspect
  memory, allocation identity, or managed object equality.
- I64 memory encoding follows the target's native little endian byte order.
  Every signed i64 bit pattern is preserved, including INT64_MIN.
- Address loads/stores use aligned eight-byte slots so the runtime can keep
  mapping bases, root addresses and metadata links without integer casts. A
  slot initially holds null. A non-null address load requires a complete prior
  address store to that same slot, with no intervening overlapping integer or
  byte write. Arbitrary integer bits must not be reinterpreted as addresses.
  The evaluator tracks this provenance and rejects invalid loads; native code
  relies on this trusted runtime precondition. Pointer bytes are never treated
  as managed roots merely because a raw address slot exists.

Verifier shape, result IDs, types, dominance, and unused instruction fields
remain mandatory. Unknown backends reject raw instructions explicitly. Map
allocates/writes memory; unmap writes memory; loads read; stores write; offset
can trap. Existing effect summaries do not establish absence of traps.

## Evaluation and acceptance

The IR evaluator uses bounded simulated mappings with zero-initialized bytes,
explicit live ownership, exact unmap pairs, and checked extents/alignment. It
does not expose host process pointers or claim to be the native allocator.
An access outside a live simulated mapping is an evaluator error. Bound total
mapping bytes independently of execution steps so malformed fixtures cannot
exhaust the host.

The native gate must actually map, write, read and unmap on macOS arm64 and
Linux arm64. Test separate mapping ownership, null/equality, signed extrema,
all byte values including NUL, alignment/range/size errors, and syscall
failure handling. Compare the evaluator with valid native runs. Generated
images must still be emitted in Rey without an external build tool or Rey C
runtime. Only after this primitive gate passes should the runtime build its
heap metadata, allocator and explicit-root collector on these operations.
