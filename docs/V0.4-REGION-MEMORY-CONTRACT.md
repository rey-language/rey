# Region-only managed memory contract, revision 1

Status: implementation contract for the v0.4 region/promotion wave, 2026-10-21.
This contract supersedes the tracing-heap and collector parts of
[V0.4-MANAGED-INTEGRATION-CONTRACT.md](V0.4-MANAGED-INTEGRATION-CONTRACT.md) for
the production managed path. The old fixed heap/collector remain historical
test components only; no production build may allocate through them, publish GC
roots, poll a collector, or fall back to tracing collection.

The release invariants are:

- No tracing collector and no reference counting in the production runtime.
- No public `malloc`/`free`, pointer arithmetic, ownership annotations, or borrow
  rules in ordinary Rey source.
- Shared mutable identity, aliases, cycles, and direct object addresses are
  preserved.
- Promotion changes the owning lifetime of an allocation group, never the
  address of an object.
- Unknown lifetimes receive an enclosing lifetime; completely unknown persistent
  escapes reach the program region.
- Ending a lifetime releases the allocation groups and metadata it still owns.
  Removing a reference never triggers collection.
- Unreachable objects in a live region may remain allocated until that region
  ends. This is accepted, bounded by cohort size, and reported.

## 1. Lifetimes and allocation groups

A lifetime is a runtime region record. The context owns one program region,
created first with a serial allocated from the owning registry, and a stack of
active invocation/iteration regions. Registry serials increase across all
contexts and do not roll back when a region ends or a context is destroyed.
Younger lifetimes have larger serials and are ended before older ones.
The program region is ended only by context destruction.

Every managed allocation site has a deterministic positive `groupId` (its
one-based ordinal in `ManagedProgram.allocations`). Objects allocated by one
site share an allocation group so unrelated scratch storage is not retained by
one escape. A group owns one or more small chunks. Chunks are never moved.

Placement order:

1. Storage elimination and scalar replacement are later optimizer sectors.
2. Stack storage is a non-moving cohort for a non-cyclic local whose address
   is not published. The object must be at most 256 bytes, must not contain a
   reference field or a variable tail, and must not be recursive. Completion
   selects it only after `stackPlacementRejection` accepts the carriers.
   Lowering allocates it in a kind-4 cohort with a 4096-byte budget and ends
   that cohort before any enclosing invocation region. The verifier rejects a
   stack object that can be stored, returned, captured, passed, or published.
3. A proven local lifetime uses an invocation or iteration region.
4. A returned-only construction may use the caller destination.
5. An unknown or persistent escape uses the program region.
6. Runtime promotion extends a group when an unproven store or return crosses a
   lifetime boundary.

The revision 1 implementation enables items 2-6. Item 2 is limited to the
proof above; a local that fails it stays in an invocation, iteration, or
program region.

## 2. Runtime object format

Object pointers are direct addresses. Each object starts with the existing
16-byte header:

- offset 0: `2^33 + layoutId` for region-owned objects (bit 33 is the managed
  region tag; the low 32 bits are the layout id).
- offset 8: payload byte length.
- offset 16: payload, with layout-declared reference fields.

Immediately before the header, eight bytes hold the address of the object's
group record. This word is runtime metadata, not part of the Rey layout. A
record is reachable in constant time as `load(object - 8)`.

Object record (64 bytes):

- 0: magic `1380272224`.
- 8: group address.
- 16: object address.
- 24: owner region address.
- 32: layout id.
- 40: payload bytes.
- 48, 56: reserved zero.

Group record (64 bytes):

- 0: magic `1380272222`.
- 8: next group in its owner region.
- 16: owner region address.
- 24: allocation-site group id.
- 32: chunk list head.
- 40: chunk count.
- 48: object count.
- 56: reserved zero.

Chunk record (64 bytes) followed by payload storage:

- 0: magic `1380272223`.
- 8: next chunk in the group.
- 16: data address.
- 24: capacity.
- 32: used bytes.
- 40: owner group address.
- 48, 56: reserved zero.

Chunks are at most 4096 bytes unless one object requires more. A group appends
objects to its current chunk with an aligned bump cursor and limit check. The
eight-byte record backpointer is reserved before each object. Zero the payload
as the current runtime does.

Region record (128 bytes):

- 0: magic `1380272221`.
- 8: next active region.
- 16: context address.
- 24: monotonically assigned registry-wide serial (including the program region).
- 32: parent region (null for the program region).
- 40: group list head.
- 48: group count.
- 56: object count.
- 64: requested chunk bytes.
- 72: ended flag (zero while active; program region stays zero).
- 80: dependency list head.
- 88: dependency count.
- 96: reserved zero through 127.

Context (288 bytes):

- 0: magic `1380272220`.
- 8: borrowed layout registry.
- 16: program region address.
- 24: active region list head (newest first).
- 32: active region count (program region included).
- 40: total promotions.
- 48: total dependency records.
- 56: total requested chunk bytes across active regions.
- 64: total live object count across active regions.
- 72-199: small-block cache heads and counts.
- 200: live allocation-group count.
- 208-255: slab list, current/spare slab, cursor, and cache state.
- 256: most recently assigned region serial in this context; initialized to the program region's registry-wide serial and bounded to `2^27 - 1` for handle encoding.
- 264: owning layout registry mapping page number, bounded to 36 bits. The registry mapping must be 4 KiB aligned and below `2^48`.
- 272: requested bytes of live direct blocks larger than 4096 bytes.
- 280: live direct-block count.

Region-end checks reject ending the program region, ending a region that is not
active, and ending a region while a younger active region remains (the existing
LIFO lifetime rule).

## 3. Runtime API

`managedMappedSlabBytes` and `managedCachedBlockBytes` report mapped slabs and their reusable cached subset. `managedMappedDirectRequestedBytes` and `managedMappedDirectBlockCount` report live large direct blocks; requested bytes exclude page rounding and are not RSS.

The registry is borrowed. Pointer-returning `region*` and `managedRegion*`
functions remain available for existing trusted runtime callers and fixtures;
their results are dereferenceable pointers and must not be retained after a
region ends or its context is destroyed.

Compiler-generated programs use a separate opaque handle API. Handle values
have the `RawAddress` ABI for compatibility with the current IR, but are integer
tokens and must never be dereferenced. Their high 36 bits identify the owning
registry's 4 KiB mapping page and their low 27 bits identify a region serial
allocated monotonically by that registry. Thus simultaneous registries have
distinct handle namespaces, and a destroyed context's serial is never reused
while its registry remains live. Handles may outlive their context, but not
their owning registry. Resolution checks both fields against active regions.
IDs fail closed before wrap. Registry mappings must be page-aligned
and below `2^48`; the runtime rejects mappings outside this range. A token must
not outlive its registry: after registry destruction, a reused mapping page
could alias an old token. The registry is borrowed by contexts and must outlive
them. Operations on each live context remain unsynchronized and require
exclusive access.

Existing pointer-compatible runtime API:

```text
managedCreate(registry: raw): raw
managedDestroy(context: raw): void
managedProgramRegion(context: raw): raw
managedCurrentRegion(context: raw): raw
managedRegionCreate(context: raw): raw
managedRegionCreateChild(context: raw, parent: raw): raw
managedRegionEnd(context: raw, region: raw): void
managedRegionAllocate(context: raw, region: raw, layoutId: int, groupId: int): raw
managedAllocateDestination(context: raw, destination: raw, layoutId: int, groupId: int): raw
managedAllocateProgram(context: raw, layoutId: int, groupId: int): raw
managedStoreReference(context: raw, object: raw, payloadOffset: int, value: raw): void
managedPromoteReference(context: raw, object: raw, target: raw): raw
managedPromotionCount(context: raw): int
managedDependencyCount(context: raw): int
managedRegionGroupCount(context: raw): int
managedLiveObjects(context: raw): int
managedLivePayloadBytes(context: raw): int
managedRequestedObjectBytes(context: raw): int
managedRegionRequestedBytes(context: raw): int
managedRegionUsedBytes(context: raw): int
managedRegionObjectCount(context: raw): int
```

The production region linker binds these generation-aware wrappers instead of
the pointer-returning `managedRegion*` operations:

```text
managedHandleRegionCreate(context: raw): raw
managedHandleRegionCreateCohort(context: raw, parent: raw, kind: int, budget: int): raw
managedHandleRegionEnd(context: raw, region: raw): void
managedHandleRegionAllocate(context: raw, region: raw, layoutId: int, groupId: int): raw
managedHandleAllocateDestination(context: raw, destination: raw, layoutId: int, groupId: int): raw
managedHandlePromoteReference(context: raw, object: raw, target: raw): raw
```

`managedHandleAllocateDestination` and `managedHandlePromoteReference` accept a
null destination to select the program region. Task records keep region tokens
internally; `taskRegionHandle` returns one, while the existing `taskRegion`
helper unwraps an active region to its legacy pointer for trusted fixtures.
`taskCreateHandle` accepts an opaque parent token; the existing `taskCreate`
entry point retains its pointer-based parent argument for compatibility.

`managedCurrentRegion` returns the newest active region; it is the program
region when no invocation region is active. Runtime helper allocation
(`managedAllocate`, `managedAllocateSized`) uses the current region, so container
operations allocate into the active invocation lifetime. `managedAllocateSized`
keeps its existing signature `(context, layoutId, payloadBytes) -> raw`.

`managedRegionAllocate`/`managedAllocateDestination` reject variable-tail
layouts. Variable tails are allocated through `managedAllocateSized` in the
current region. `destination == null` in `managedAllocateDestination` means the
program region.

`managedPromoteReference(context, object, target)` promotes the object's group,
and every younger dependency required by the target lifetime, to `target`.
`target == null` means the program region. Addresses never change. A null
`object` is a no-op returning null; nullable returns do not require a synthetic
object. An older or equal source lifetime is also a no-op returning the same
address. A younger source is re-homed to the older target.

`managedStoreReference` validates the owner, the offset, and the value. It
promotes the value's group to the owner region when the value is younger than
the owner. It records a region dependency from the owner region to the value
region even when the value is already older. It publishes the field only after
promotion and dependency recording complete. A null value needs no promotion.
Storing a region reference into a program-region object promotes the value to
the program region.

No `managedRoot*`, `managedCollect`, GC range registration, collection safepoint,
allocation budget, stress collection, or heap import may appear in the production
managed runtime. For source compatibility with the frozen container module the
old root helpers may exist as non-collecting compatibility shims that validate
the context and return zero/void, but the generated region path must not call
them and the linker must not bind them as roots. They are not a fallback
collector and never publish a root.

## 4. Dependency and promotion protocol

A dependency edge is `owner region -> value region`, recorded on the first
reference store between those regions. Duplicate edges are coalesced. The edge
exists even when the value region is already older.

Promotion of region `A` to target `T`:

1. Validate `A` and `T` and that both are active. If `A` is older than or equal
   to `T`, return the object unchanged; promotion only re-homes a younger source.
2. Re-home every group owned by `A` to `T`; append it to `T`'s group list.
   Chunk addresses, object addresses, and all aliases stay unchanged.
3. Walk `A`'s dependency edges. For each child `B` that is younger than `T`,
   promote `B` to `T` recursively.
4. Record the resulting `T -> B` edges so later promotion of `T` is transitive.
5. Publish the original reference only after all of this completes.
6. Handle cycles with canonical region identities and a visited worklist. Do not
   recurse through unbounded graph walks; the dependency graph is region-level.

Ending region `A` releases every chunk still owned by a group whose owner is
`A`. Promoted groups have already moved and are not released. Dependency records
owned by `A` are released. The walk follows recorded region relationships only;
it never scans objects for reachability.

Dependency and promotion work is reported separately from object bytes:

- `managedPromotionCount`
- `managedDependencyCount`
- `managedRegionGroupCount`

## 5. Compiler-side plan and verifier

`ir::managed::placement` keeps `ManagedStorage::Region` for a proven invocation
lifetime, `ManagedStorage::Destination` for a returned-only construction, and the
existing `Heap` spelling as the program-region placement for unknown/persistent
escapes. The compiler-owned region path must map that spelling to
`managedAllocateProgram`, never to a tracing allocation. A later cleanup may
rename the enum; the semantics above are normative now.

Placement remains conservative:

- A reference argument or unknown callee escapes to the program region.
- An owner's escape propagates to references stored in it.
- A returned stored field keeps its owner and child in the program region.
- CFG-cycle allocation sites use the program region until an iteration-lifetime
  proof exists.
- A returned fresh component with only return escape may use the destination.
- No placement may publish a stack object.

Named container hooks and `managedAllocateSized` are precise. A fresh container
or string follows its uses: no escape stays in the allocating function's
invocation or iteration region; a return-only escape uses the caller
destination; a value retained by a caller that does not publish it further is
placed in that caller's region. Lowering passes that region as the callee
destination and promotes the returned reference before the callee region ends,
so the callee's stack cohort is not retained with the container. Contents
stored into a fresh container or into such a call result follow that same
lifetime instead of being forced into the program region.

An unknown callee still publishes every reference argument and every returned
reference to the program region. A reference parameter that this function
cannot see the allocation of stays on that conservative rule when it is stored
into. Hook storage itself still uses the current region, which is the
destination cohort when the caller proved the retention.

`ir::managed::lifetime` verifies a placement plan before lowering:

- Every allocation has a known placement.
- A `Region` allocation cannot be returned unless it is promoted first or its
  escape is proven to stay inside the invocation.
- A `Destination` allocation is only reachable from its return value.
- A `Stack` allocation (when introduced) has no store, return, capture, call
  argument, global, or task escape.
- Every reference store that crosses lifetimes has a promotion path through the
  runtime store hook; a direct raw store bypass is rejected.
- Every region end dominates all uses of its objects.
- Recursive/cyclic placement is rejected when the proof is not established.

The verifier returns a contextual diagnostic, never a partial plan.

## 6. Lowering and linking

`ir::managed::regions::lowerManagedRegions(module, bindings, placements)` returns
a fresh verified `IRProgram`:

- Append hidden context and destination raw parameters to every user function.
- Create an invocation region at entry only for functions marked in
  `placement.regionFunctions`. For every reference return, insert promotion to
  the hidden destination before region end, then end the region. A null object
  is a promotion no-op; a null destination means the program region.
- Rewrite allocation hooks:
  - `Region` -> `managedRegionAllocate(context, region, layoutId, groupId)`
  - `Destination` -> `managedAllocateDestination(context, destination, layoutId, groupId)`
  - `Heap` -> `managedAllocateProgram(context, layoutId, groupId)`
- Rewrite reference stores to `managedStoreReference(context, owner, offset, value)`.
- Pass hidden context/destination arguments to user calls.
- Insert no root push/set/pop and no collection call.
- Generate the same no-argument entry wrapper: register layouts, create context,
  call original main with the context and null destination, destroy context,
  release registry.
- `groupId` is the one-based ordinal of the allocation annotation, emitted as an
  i64 constant.

The compiler's opt-in `--selfhost-fast-exit` ends its own process after a
successful trusted output write. The OS reclaims its mappings; the wrapper does
not run, so its teardown integrity checks are skipped. This does not change the
generated wrapper for ordinary programs or normal compiler invocations.

`ir::managed::regionlink` (or the existing link module) loads
`runtime-rey/regions/main.rey`, `runtime-rey/managed/main.rey`,
`runtime-rey/layout/main.rey`, and `runtime-rey/containers/main.rey`; validates
exact function identities and signatures; remaps runtime function ids; and
returns region bindings. The production build must not load `gc` or `heap`.

The driver exposes `--regions` as the default managed path. `--no-regions` may
remain only as a legacy experiment for the old tests; it is not a production
path and must not be used for v0.4 acceptance. `--gc-stress` is removed from the
region driver. A `--promotion-stress` flag may force a promotion check before
each user call for tests; it must not collect.

## 7. Validation obligations

Write fixtures before running any compiler, build, test, or benchmark:

- Allocation group reuse across calls and distinct group separation.
- Function region end releases only its remaining groups.
- Program region survives function returns and is released by context destroy.
- Promotion preserves object address and alias identity.
- Repeated promotion is idempotent.
- Older/equal source promotion is a no-op: same address, unchanged group
  ownership, and unchanged promotion/dependency counters.
- Promotion walks one dependency chain and a cyclic dependency graph.
- Storing a younger value into an older owner promotes before publication.
- Storing an older value into a younger owner records the dependency without
  promoting.
- Destination construction preserves alias identity and survives the callee.
- Returned unknown escapes reach the program region.
- Region-end rejection with a live younger region.
- Region-end rejection for the program region and double end.
- Container string/vector/map allocation in the current region.
- Null promotion is a no-op, including nullable reference returns; no synthetic
  object is created.
- Container method use and cross-boundary container returns preserve identity,
  aliases and cycles under conservative program-region placement.
- No generated program contains `managedCollect`, root publication, GC range
  registration, heap allocation, or an import of the historical collector.
- Repeated fixed-size requests with no persistent escape plateau after warm-up.
- An explicit long-lived graph-retention fixture reports retained bytes.

The global barrier rule applies: every sector writes implementation and fixtures
before any build or execution. The coordinator then runs the frozen gates,
repairs integration defects, and records evidence in
[V0.4-REGION-VALIDATION.md](V0.4-REGION-VALIDATION.md).

## 8. Out of scope for this revision

- Moving collection or compaction.
- Detached tasks. Scoped task regions and join/cancellation are the next
  concurrency sector.
- SIMD, register allocation, and machine-IR optimization.
- Windows/PE and native x64 hardware validation.
- A claim that region retention is bounded for arbitrary long-lived graphs.
